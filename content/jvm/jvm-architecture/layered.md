## Quick

`javac` dịch `.java` thành [[bytecode]] trong [[class-file|class file]]; [[jvm|JVM]] nạp class khi cần, chạy bytecode bằng [[interpreter|interpreter]], rồi [[jit|JIT]] biên dịch phần chạy nhiều thành mã máy. [[jdk|JDK]] = JVM + thư viện chuẩn + công cụ (`javac`, `jcmd`, `jlink`...). **Class file mang số phiên bản, và chỉ `--release N` mới bắt compiler kiểm API theo đúng Java N, nên luôn biên dịch bằng `--release N` với N là phiên bản Java chạy trên production.**

## Interview

**Ba khái niệm**: JVM là máy ảo theo đặc tả JVMS; [[hotspot-jvm|HotSpot]] là bản cài đặt dùng trong gần như mọi bản JDK phổ biến. [[jre|JRE]] là JVM cộng thư viện chuẩn, đủ để chạy. JDK là JRE cộng công cụ phát triển và chẩn đoán. Từ JDK 11, Oracle không phát hành JRE riêng; muốn runtime gọn thì tạo bằng [[jlink|jlink]], hoặc dùng image JRE của Temurin.

**Từ code tới mã máy**: `javac` sinh class file gồm magic `CAFEBABE`, major version (52 là Java 8, 61 là 17, 65 là 21, 69 là 25), constant pool và bytecode của từng method. Bytecode là lệnh cho máy ngăn xếp: `iload`, `iadd`, `invokevirtual`, không gắn với CPU nào. Class được nạp ở lần dùng đầu, được verifier kiểm tra, rồi chạy bằng interpreter. Method chạy nhiều được [[tiered-compilation|biên dịch theo tầng]]: C1 biên dịch nhanh kèm thu profile, C2 tối ưu mạnh dựa trên profile đó. Giả định sai thì JVM bỏ mã máy, quay về interpreter. Vì vậy ứng dụng Java cần warmup: vài phút đầu chậm hơn lúc chạy ổn định.

**Bẫy hay gặp**: build bằng JDK mới nhưng chạy JVM cũ. Class file mới hơn JVM thì nạp lỗi ngay với `UnsupportedClassVersionError`. Nguy hiểm hơn là `-source 17 -target 17` mà không có `--release`: compiler kiểm tra theo thư viện của JDK đang build, nên dùng được `List.getFirst()` của Java 21; class vẫn ghi version 61, khởi động bình thường trên Java 17, tới lúc gọi mới ném `NoSuchMethodError`.

**Làm đúng**: Maven đặt `maven.compiler.release`, Gradle dùng toolchain; image chạy dùng cùng phiên bản với `--release`. Production chọn bản [[lts|LTS]] (17, 21, 25) của một nhà phát hành build từ [[openjdk|OpenJDK]] (Temurin, Corretto, Zulu, Microsoft...) và cập nhật bản vá mỗi quý.

## Deep

- **Đọc class file**: `javap -v Foo.class | grep major` ra phiên bản; công thức là phiên bản Java + 44 (JDK 27 sinh major 71, đã kiểm). `javap -c` in bytecode. Thông điệp khi class mới hơn JVM (đã chạy với class sửa thành 73 trên JDK 27): `UnsupportedClassVersionError: Hello has been compiled by a more recent version of the Java Runtime (class file version 73.0), this version of the Java Runtime only recognizes class file versions up to 71.0`. Lỗi này xảy ra lúc nạp class, nên thư viện chỉ dùng ở một nhánh hiếm vẫn có thể nổ muộn.
- **`--release` khác `-source`/`-target` thế nào**: `-source` chọn cú pháp, `-target` chọn version class file, còn API được kiểm theo thư viện của JDK đang chạy `javac`. `--release N` (JDK 9, JEP 247) kiểm API theo bảng chữ ký của Java N đóng sẵn trong JDK. JDK cảnh báo khi thiếu nó; câu chữ khác nhau giữa các bản: JDK 21 in `system modules path not set in conjunction with -source 17`, JDK 27 in `location of system modules is not set in conjunction with -source 17`. Ví dụ kinh điển: build bằng JDK 9+ với `-target 8`, `ByteBuffer.flip()` được ghi là trả `ByteBuffer` (kiểu trả covariant thêm ở Java 9), chạy trên Java 8 ném `NoSuchMethodError: java.nio.ByteBuffer.flip()Ljava/nio/ByteBuffer;`. JDK 27 nhận `--release` từ 8 trở lên, báo 8 là obsolete.
- **Bytecode cho thấy điều mã nguồn che đi**: `counter++` trên field `static` thành bốn lệnh `getstatic`, `iconst_1`, `iadd`, `putstatic`, nên không nguyên tử (bài Race condition, atomicity & thread-safe). Ghép chuỗi `"total=" + total` từ Java 9 là một lệnh [[invokedynamic|invokedynamic]] gọi `makeConcatWithConstants` (JEP 280); code biên dịch cho Java 8 thì thấy `StringBuilder`. Biến cục bộ là các "slot" đánh số (`iload_1`, `istore_2`), tên biến chỉ có khi biên dịch với `-g`.
- **Vòng đời của class**: loading (đọc byte) → linking (verify bytecode, prepare cấp giá trị mặc định cho field `static`, resolve tham chiếu) → initialization (chạy khối `static` và gán field, tức `<clinit>`). Initialization chỉ chạy ở lần dùng chủ động đầu tiên và JVM đảm bảo chạy đúng một lần, an toàn giữa các thread; holder idiom của singleton dựa vào điều này. Ngoại lệ trong `static` thành `ExceptionInInitializerError` ở lần đầu, các lần sau là `NoClassDefFoundError` khó hiểu. Delegation và fat jar ở bài ClassLoader.
- **Interpreter chậm cỡ nào**: vòng lặp 50 triệu phép tính trên JDK 27 (Apple M4): mặc định 18 ms mỗi vòng sau warmup, `-Xint` (chỉ interpreter) khoảng 250 ms, chậm hơn khoảng 14 lần. `-XX:+PrintCompilation` cho thấy method qua tầng 3 (C1 có profile) rồi tầng 4 (C2), dấu `%` là OSR (thay mã của vòng lặp đang chạy dở), `made not entrant` là bỏ mã đã biên dịch. Inlining, escape analysis, deopt và JMH ở bài JIT compiler.
- **Cách JDK phát hành**: mỗi sáu tháng một bản (tháng 3 và tháng 9) từ Java 10; LTS hai năm một lần từ 17: 17 (2021), 21 (2023), 25 (2025), kế tiếp 29 (2027). JDK 27 (9/2026) không phải LTS, chỉ có vá tới khi JDK 28 ra. Production dùng bản không LTS là cam kết nâng cấp sáu tháng một lần.
- **Nhà phát hành**: OpenJDK là mã nguồn; Temurin (Eclipse Adoptium), Amazon Corretto, Azul Zulu, Microsoft Build of OpenJDK, Red Hat, BellSoft Liberica, Oracle là các bản build qua bộ kiểm tra tương thích (TCK). Khác nhau ở thời gian hỗ trợ, bản vá backport và phần thêm (Liberica có bản kèm JavaFX). Eclipse OpenJ9 (IBM Semeru) là một JVM khác hẳn HotSpot: tốn ít RAM hơn, cờ và công cụ khác (`-Xshareclasses`), nên kinh nghiệm tuning HotSpot không chép sang được. GraalVM thêm JIT Graal và [[native-image|native image]] (bài Khởi động nhanh).
- **Giấy phép Oracle JDK**: từ 17, bản LTS dùng điều khoản NFTC, miễn phí cả production tới một năm sau khi LTS kế tiếp ra; sau đó bản vá chuyển sang giấy phép OTN, dùng production phải mua subscription. JDK 21 hết NFTC từ 9/2026, JDK 25 tới 9/2028. Nhóm không muốn theo dõi giấy phép thường chọn Temurin hoặc Corretto.
- **Không còn client/server VM**: JDK 64 bit chỉ có Server VM; `-client` bị bỏ qua. Bản x86 32 bit bị gỡ khỏi JDK 25 (JEP 503).
- **`jlink` và image nhỏ**: `jdeps --print-module-deps app.jar` liệt kê module cần, `jlink --add-modules ... --strip-debug --no-header-files --no-man-pages` tạo runtime chỉ gồm các module đó. Thiếu module (ví dụ `java.naming` cho JNDI, `jdk.unsupported` cho thư viện dùng `sun.misc.Unsafe`) chỉ lộ ra lúc chạy tới đoạn code cần nó, nên phải chạy test trên đúng image.
- **Chạy file nguồn trực tiếp**: `java OrderService.java` biên dịch trong bộ nhớ rồi chạy (JEP 330, Java 11); từ Java 22 (JEP 458) chạy được chương trình nhiều file. Tiện cho script và thử nhanh, không thay quy trình build.
- **Preview feature**: code dùng tính năng preview phải biên dịch và chạy với `--enable-preview`, class file có minor version 65535 và chỉ chạy trên đúng phiên bản JDK đó. Không dùng preview trong thư viện chia sẻ.
- **Kiểm tra JVM đang chạy**: `java -version` trong image, `jcmd <pid> VM.version` với process đang chạy, `Runtime.version()` trong code. Công cụ đầy đủ ở bài Bộ công cụ chẩn đoán JVM. Kotlin, Scala cũng sinh bytecode và có cùng bẫy: `jvmTarget` của Kotlin phải khớp JVM chạy.
