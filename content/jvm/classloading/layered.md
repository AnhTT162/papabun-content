## Quick

[[classloader|ClassLoader]] biến byte của class file thành class trong JVM. **Một class được xác định bằng tên đầy đủ cộng với classloader đã định nghĩa nó**: cùng `com.shop.Order` nạp bởi hai loader là hai kiểu khác nhau. Mặc định loader hỏi loader cha trước ([[parent-delegation|parent delegation]]), nên class của JDK không bị thay. Class chỉ được gỡ khỏi [[metaspace|metaspace]] khi **cả loader của nó không còn với tới được**; một tham chiếu sót lại giữ toàn bộ class của loader đó.

## Interview

**Cây loader**: bootstrap (trong JVM, nạp `java.base` và một số module lõi như `java.logging`, `java.xml`; `getClassLoader()` trả `null`) → platform (phần còn lại của JDK như `java.sql`; thay extension loader từ Java 9) → app ([[classpath]]). Ứng dụng có thể tạo loader con: Tomcat cho mỗi webapp, Spring Boot cho fat jar, plugin engine cho mỗi plugin.

**Delegation**: `loadClass` xem class đã nạp chưa, hỏi cha, cha không thấy mới tự tìm (`findClass`). Nhờ vậy `java.lang.String` luôn là một. Ngoại lệ có chủ đích: webapp của Tomcat nạp class của mình trước (child-first), trừ class của JDK và Servlet API.

**Hệ quả của danh tính**: object tạo bởi loader A không ép được sang class cùng tên của loader B: `ClassCastException: class X cannot be cast to class X`, thông điệp ghi rõ hai loader. Hay gặp với DevTools restart của Spring Boot khi object được deserialize bằng loader khác.

**[[fat-jar|Fat jar]] của Spring Boot**: `java -jar` chạy `JarLauncher`, nó tạo `LaunchedClassLoader` đọc `BOOT-INF/classes` và jar lồng trong `BOOT-INF/lib`. App loader chỉ thấy chính file jar, không thấy class của bạn. Code dùng [[context-classloader|thread context classloader]] (`ServiceLoader`, JAXB) chạy trên thread của [[common-pool|common pool]], vốn có context loader là app loader, sẽ không tìm thấy thư viện: chạy trong IDE được, chạy jar thì lỗi.

**Rò classloader**: plugin hay script được nạp lại bằng loader mới; loader cũ chỉ được thu hồi (và class được gỡ, [[class-unloading|class unloading]]) khi không còn object, class hay tham chiếu nào tới nó. Một [[thread-local|`ThreadLocal`]] trên thread của pool, một registry `static` ở loader cha, một thread do plugin khởi chạy là đủ giữ hàng trăm class. Metaspace tăng mỗi lần reload tới `OutOfMemoryError: Metaspace`.

**Chẩn đoán**: `jcmd <pid> VM.classloader_stats` (số loader, số class mỗi loader), histogram có cùng tên class lặp nhiều lần, `-Xlog:class+unload` không in gì; heap dump rồi Path to GC Roots của một loader cũ để biết ai giữ nó.

## Deep

- **Thuật toán `loadClass`** (`ClassLoader.loadClass`): `findLoadedClass` → `parent.loadClass` → `findClass` → `defineClass`. Loader tự viết nên ghi đè `findClass`, không ghi đè `loadClass`, để giữ delegation. Từ Java 7, loader gọi `registerAsParallelCapable()` khoá theo từng tên class thay vì khoá cả loader; loader cũ khoá cả object từng gây deadlock khi hai loader nạp chéo nhau.
- **Java 9 trở đi**: các loader dựng sẵn biết package nào thuộc module nào và giao thẳng cho loader của module đó trước khi hỏi cha. `jre/lib/ext` và `-Djava.ext.dirs` bị bỏ (JVM từ chối khởi động nếu còn đặt). Thứ tự classpath và [[jpms|JPMS]] ở bài Classpath, JPMS & xung đột dependency; vòng đời load → link → init ở bài JDK, JRE, JVM & bytecode.
- **`Class.forName(name)` khác `loader.loadClass(name)`**: `forName` dùng loader của class gọi và chạy khối `static` (initialize); `loadClass` chỉ nạp. `Class.forName(name, false, loader)` để chọn cả hai. Idiom `Class.forName("org.postgresql.Driver")` cũ là để chạy `static` đăng ký driver; JDBC 4 tự tìm qua [[service-loader|`ServiceLoader`]].
- **Danh tính class, đã chạy trên JDK 27**: `rules.jar` nằm trên classpath, đồng thời được nạp lại bằng một `URLClassLoader` tên `restartedMain` có cha là platform loader (bỏ qua app loader), rồi ép object của loader đó sang class của app loader: `ClassCastException: class com.example.rules.Rule0 cannot be cast to class com.example.rules.Rule0 (com.example.rules.Rule0 is in unnamed module of loader 'restartedMain' @7e9e5f8a; com.example.rules.Rule0 is in unnamed module of loader 'app')`. Mỗi bên có field `static` riêng, nên "singleton" là một bản cho mỗi loader. Khi hai loader chia sẻ kiểu qua chữ ký method mà mỗi bên nạp một bản, JVM ném `LinkageError: loader constraint violation`.
- **Reload không có tác dụng vì parent-first**: plugin jar cũng nằm trên classpath của ứng dụng thì `URLClassLoader` mới hỏi app loader trước và nhận lại class cũ. Đã chạy: hai loader cho ra cùng một `Class`, loader là `AppClassLoader`. Plugin phải nằm ngoài classpath, hoặc loader phải child-first cho package của plugin.
- **Fat jar Spring Boot, đã chạy với Boot 4.1.2** (loader mới từ 3.2): manifest `Main-Class: org.springframework.boot.loader.launch.JarLauncher`, `Start-Class` là class `main` của bạn; `java.class.path` chỉ là `app.jar`; `ClassLoader.getSystemClassLoader().loadClass("demo.Main")` ném `ClassNotFoundException`. Resource có URL `jar:nested:/.../app.jar/!BOOT-INF/classes/!/data/regions.txt`, nên `new File(url.toURI())` ném `IllegalArgumentException: URI is not hierarchical`: đọc resource bằng `getInputStream()`, không bằng `File`. Bản trước 3.2 dùng `org.springframework.boot.loader.JarLauncher` và URL dạng `jar:file:...!/BOOT-INF/lib/x.jar!/`. `LaunchedClassLoader` vẫn parent-first: jar đứng trên classpath của JVM nằm ở app loader và thắng bản trong `BOOT-INF/lib`: điều này xảy ra khi chạy `java -cp app.jar:extra.jar org.springframework.boot.loader.launch.JarLauncher` hoặc khi agent (`-javaagent`) mang thư viện theo; còn `java -jar` thì bỏ qua `-cp`.
- **Thêm jar ngoài vào fat jar**: `PropertiesLauncher` với `-Dloader.path=plugins/` (layout `ZIP`). Muốn bỏ launcher thì giải nén (Boot 3.3+): `java -Djarmode=tools -jar app.jar extract` cho ra thư mục chạy bằng classpath thường, khởi động nhanh hơn và dùng được CDS (bài Khởi động nhanh: CDS, CRaC, GraalVM native).
- **Thread context classloader (TCCL)**: thư viện nạp class "của người dùng" theo tên thường dùng `Thread.currentThread().getContextClassLoader()`: `ServiceLoader.load(Class)`, JAXB, JNDI, nhiều framework cũ. Thread mới nhận TCCL của thread tạo ra nó (đã chạy: pool `Executors.newFixedThreadPool` và virtual thread đều nhận loader của `main`). Worker của common pool thì luôn có TCCL là app loader (đã chạy trên JDK 27): trong fat jar, `ServiceLoader.load(PriceFormatter.class)` trên `main` tìm thấy provider, trong `CompletableFuture.runAsync` thì không. Parallel stream còn khó thấy hơn vì thread gọi cũng chạy một phần việc: lỗi chỉ xảy ra với phần tử rơi vào worker.
- **Cách tránh lỗi TCCL**: truyền executor riêng cho `CompletableFuture` (bài CompletableFuture); truyền loader tường minh `ServiceLoader.load(Spi.class, Spi.class.getClassLoader())`; tạo object đắt như `JAXBContext` một lần lúc khởi động (nó thread-safe) thay vì trong task; đặt TCCL trong `try`/`finally` khi buộc phải chạy trên thread lạ.
- **DevTools**: `RestartClassLoader` nạp class trong project (thư mục `target/classes`), jar thư viện nằm ở base loader và không nạp lại khi restart. Thư viện deserialize bằng loader của nó (`ObjectInputStream`, `JdkSerializationRedisSerializer` không cấu hình loader) tạo ra object của base loader, ép sang class của restart loader thì `ClassCastException` cùng tên. Cách xử lý: cấu hình serializer dùng loader của ứng dụng, hoặc tắt restart (`spring.devtools.restart.enabled=false`).
- **Rò metaspace, đã tái hiện trên JDK 27**: engine reload 300 class rule bằng `URLClassLoader` mới, chạy trên pool 8 thread; class rule có `static ThreadLocal<Scratch>` với `Scratch` là class của plugin. Value trỏ tới class của plugin, class trỏ tới loader, loader trỏ tới mọi class, kể cả class giữ `ThreadLocal` làm key: entry không bao giờ thành stale. Mỗi lần reload thêm khoảng 1,7 MB metaspace; `-XX:MaxMetaspaceSize=128m` thì `OutOfMemoryError: Metaspace` ở lần reload thứ 76. Sau 60 lần reload, histogram có 60 dòng `com.example.rules.RuleSet$Scratch` (mỗi dòng 8 instance, đúng số thread), `VM.classloaders` in `java.net.URLClassLoader (+ 59 more)`. Dùng pool mới cho mỗi thế hệ rule (shutdown pool cũ) thì sau 300 lần reload đã gỡ 90.597 class, metaspace 3 MB.
- **`close()` của `URLClassLoader`** chỉ đóng file jar đang mở; không đóng vẫn gỡ class được khi loader hết được tham chiếu (đã chạy: kết quả như trên). Đóng vẫn nên làm để không giữ file descriptor, và trên Windows để xoá được file jar.
- **Ai hay giữ loader cũ**: `ThreadLocal` trên thread không thuộc plugin; thread do plugin khởi chạy (thread giữ class của `Runnable` và TCCL của nó); driver JDBC đăng ký vào `DriverManager` (Tomcat log `registered the JDBC driver [...] but failed to unregister it when the web application was stopped`); listener, MBean, shutdown hook, cache `static` ở loader cha có key là `Class` của plugin. Redeploy trong Tomcat ngoài từng là nguồn chính của rò kiểu này; ứng dụng chạy container restart cả JVM nên ít gặp, nhưng plugin, script engine và hot reload vẫn gặp.
- **Sinh class động**: biên dịch script Groovy hay biểu thức mỗi request, tạo proxy ByteBuddy/CGLIB mới cho mỗi lần gọi thay vì cache, đều tạo class mới; số class nạp (`jvm.classes.loaded` của Micrometer) tăng mãi là dấu hiệu sớm. `Proxy.newProxyInstance` cache class proxy theo loader và danh sách interface nên không tăng. Lambda là [[hidden-class|hidden class]] gắn với class chứa nó.
- **Gỡ class cần GC có unload**: G1 gỡ ở cuối concurrent mark hoặc Full GC, ZGC và Shenandoah trong chu kỳ đồng thời; `MetaspaceSize` chỉ là ngưỡng kích hoạt GC (bài Vùng nhớ của JVM). GC log khi metaspace đầy: `Pause Full (Metadata GC Threshold)` rồi `Pause Full (Metadata GC Clear Soft References)` lặp lại mà không giảm được gì. Đặt `MaxMetaspaceSize` để rò thành lỗi có tên thay vì RSS tăng tới OOMKilled. Trong MAT, "Duplicate Classes" và histogram nhóm theo classloader cho thấy loader nào đang giữ bản sao.
