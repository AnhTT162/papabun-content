## Quick

Có ba cách một chương trình chờ I/O. [[blocking-io|Blocking]]: thread gọi `read` và ngủ tới khi có dữ liệu, nên mỗi kết nối cần một thread. [[io-multiplexing|I/O multiplexing]] ([[epoll]] trên Linux, kqueue trên macOS): socket để non-blocking, một thread hỏi kernel "socket nào đang sẵn sàng" rồi chỉ xử lý những cái đó; đây là nền của [[reactor-pattern|reactor]] (Netty, Nginx, Node.js, Redis). Async thật ([[io-uring|io_uring]], IOCP): gửi yêu cầu cho kernel làm rồi nhận kết quả khi xong. **Multiplexing cho vài thread giữ hàng chục nghìn kết nối, đổi lại không được chặn [[event-loop|event loop]] dù chỉ vài chục mili giây; virtual thread của Java đem lợi ích đó cho code blocking bình thường.**

## Interview

**Thread-per-connection**: dễ viết, dễ debug, stack trace rõ. Giới hạn ở số thread: mỗi platform thread có stack riêng (mặc định 1 MB không gian địa chỉ trên Linux x64), tốn bộ nhớ kernel và [[context-switch|context switch]] khi có hàng nghìn thread chờ I/O. Đây là bài toán [[c10k|C10K]].

**Multiplexing**: `epoll_ctl` đăng ký socket một lần, `epoll_wait` trả về danh sách socket sẵn sàng, chi phí theo số socket có sự kiện chứ không theo tổng số socket như `select`/`poll`. Java NIO `Selector` dùng epoll trên Linux và kqueue trên macOS (`sun.nio.ch.KQueueSelectorImpl`, đã chạy trên JDK 27).

**Reactor**: một hay vài event loop, mỗi loop vòng lặp `chờ sự kiện → đọc → giải mã → gọi handler → ghi`. Netty có boss group nhận kết nối và worker group xử lý đọc ghi; mỗi kết nối gắn cố định với một event loop. Handler chặn thì mọi kết nối của loop đó đứng chờ.

**Async (proactor)**: io_uring có hai ring buffer chia sẻ với kernel: ứng dụng ghi yêu cầu vào submission queue, kernel trả kết quả vào completion queue, ít syscall hơn và làm được cả file. Netty có transport io_uring; JDK chưa dùng nó mặc định.

**[[virtual-thread|Virtual thread]]**: code blocking bình thường, nhưng khi đọc socket chưa có dữ liệu, JDK gỡ virtual thread khỏi carrier và đăng ký socket với poller (epoll, kqueue) bên dưới. Được cả hai: viết kiểu tuần tự, quy mô gần như event loop.

**[[zero-copy|Zero-copy]]**: `FileChannel.transferTo` dùng `sendfile`, dữ liệu đi từ [[page-cache|page cache]] ra socket không qua bộ nhớ của ứng dụng (Kafka dùng cách này, bài Kiến trúc Kafka).

**Bẫy hay gặp**: gọi JDBC, `RestTemplate`, `Thread.sleep` trên event loop; nghĩ non-blocking làm việc CPU nhanh hơn; dùng reactive chỉ để "cho nhanh" khi service chỉ có 200 request đồng thời.

**Cách làm đúng**: blocking hoặc virtual thread cho service CRUD thường; event loop cho proxy, gateway, hàng chục nghìn kết nối dài; việc chặn luôn chuyển sang pool riêng.

## Deep

- **Chặn event loop, số đo**: một event loop NIO, mỗi request "gọi database" 50 ms ngay trong loop, 20 client gửi cùng lúc: latency min 63 ms, p50 640 ms, max 1.166 ms, vì request thứ 20 chờ 19 request trước. Chuyển phần 50 ms sang pool 32 thread rồi trả kết quả về loop ghi: min 58, p50 65, max 70 ms (đã chạy trên JDK 27 macOS). Trong Spring WebFlux, dấu hiệu và cách bắt bằng [[blockhound|BlockHound]] ở bài Spring WebFlux & Netty.
- **Level-triggered và edge-triggered**: level-triggered (mặc định của epoll, của Java NIO) báo lại mỗi lần `epoll_wait` khi socket còn dữ liệu chưa đọc; edge-triggered chỉ báo khi có dữ liệu mới tới, dữ liệu cũ còn nằm trong buffer thì không báo lại, nên phải đọc tới khi `read` trả `EAGAIN`, đọc thiếu là kết nối treo im lặng. Transport epoll native của Netty dùng edge-triggered mặc định, ít lần thức dậy hơn.
- **File không multiplex được**: `epoll_ctl` từ chối file thường (`EPERM`), còn `select`/`poll` luôn báo file thường là sẵn sàng; cả hai đều không giúp gì, vì `read` vẫn chặn khi dữ liệu chưa có trong page cache. Vì vậy Netty, Node.js (libuv) đẩy I/O file sang thread pool. Virtual thread đọc file thì chiếm (capture) carrier trong lúc chờ đĩa, và JDK bù bằng cách tạm tăng parallelism của scheduler; khác với pinning, vốn không được bù. Trên Linux, io_uring là cách thực dụng để làm file I/O bất đồng bộ thật (AIO cũ chỉ ổn với `O_DIRECT`); Windows có IOCP.
- **Virtual thread bên trong**: socket của virtual thread được đặt non-blocking; `read` chưa có dữ liệu thì virtual thread unmount và socket được đăng ký với poller thread của JDK (`jdk.readPollers`), có dữ liệu thì virtual thread được lên lịch lại. Bị pin (Java 21–23 trong `synchronized`, hoặc native) thì quay về chặn carrier. Chi tiết pinning, giới hạn và quan sát ở bài Virtual Threads chuyên sâu.
- **Một event loop là một thread**: Redis xử lý lệnh tuần tự trên một thread, nên một lệnh O(n) như `KEYS *` hay `HGETALL` khoá lớn chặn mọi client (bài Redis bên trong). Node.js cũng vậy với vòng tính toán dài. Việc CPU nặng trong mô hình event loop phải chia nhỏ hoặc chuyển sang worker.
- **`select`, `poll`, `epoll`**: `select` giới hạn fd dưới `FD_SETSIZE` (1024) và mỗi lần gọi phải chép cả tập fd vào kernel rồi quét O(n); `poll` bỏ giới hạn 1024 nhưng vẫn O(n) mỗi lần; epoll giữ danh sách quan tâm trong kernel và chỉ trả socket có sự kiện. Với 10.000 kết nối mà 50 cái có dữ liệu, epoll trả 50, `poll` quét 10.000.
- **io_uring trong thực tế**: nhanh nhất khi I/O rất nhiều và nhỏ (ít syscall, gom lô), nhưng đã có nhiều lỗ hổng kernel; profile seccomp mặc định của Docker chặn các syscall io_uring, và nhiều nền tảng tắt nó. Kiểm tra môi trường chạy trước khi chọn transport io_uring; transport epoll hoặc NIO vẫn là lựa chọn an toàn.
- **Zero-copy chi tiết**: đường thường đọc file rồi ghi socket chép dữ liệu bốn lần (đĩa → page cache → user space → socket buffer → card mạng) qua hai syscall, tức bốn lần chuyển giữa user và kernel; `sendfile` bỏ hai lần chép qua user space. TLS phá tối ưu này vì dữ liệu phải được mã hoá trong user space, trừ khi dùng kTLS (mã hoá trong kernel); `SSLEngine` của JDK không dùng kTLS, nên Kafka bật TLS là mất `sendfile`. `mmap` (`FileChannel.map`) là cách khác: ánh xạ file vào bộ nhớ, đọc như mảng; nhanh với đọc ngẫu nhiên, nhưng lỗi I/O thành `InternalError`/`SIGBUS` và bộ nhớ ánh xạ không nằm trong heap.
- **[[backpressure|Backpressure]] là việc của bạn**: event loop đọc nhanh hơn downstream xử lý thì dữ liệu dồn trong bộ nhớ. Netty có `Channel.isWritable()` và watermark của buffer ghi; đọc thì tắt `autoRead` khi downstream chậm. Thread-per-connection có backpressure tự nhiên: thread bận thì không đọc tiếp, TCP flow control đẩy ngược về client (bài TCP chuyên sâu).
- **Chọn mô hình**: service gọi database và vài API, vài trăm request đồng thời: Spring MVC với thread pool, hoặc bật virtual thread trên Java 21+. Gateway, proxy, WebSocket hay SSE với hàng chục nghìn kết nối dài, nhiều fan-out song song: event loop (WebFlux, Netty, Vert.x) hoặc virtual thread nếu thư viện không pin. Đo trước: phần lớn service không bị giới hạn ở số thread mà ở database và downstream (bài Ứng dụng Java CPU 100%, bài Profiling).
- **Quan sát**: thread dump của ứng dụng event loop chỉ có vài thread `epollWait`/`kevent` hầu hết thời gian, nên thread dump ít giá trị; latency phải đo theo từng request, và phải có metric thời gian chờ trong hàng đợi của event loop (Netty `pendingTasks`). Với virtual thread, `jstack` không thấy chúng; dùng `jcmd <pid> Thread.dump_to_file`. Ở tầng kernel, thread blocking chờ socket ở trạng thái `S`, chờ đĩa ở `D` (bài Lệnh Linux để điều tra sự cố).
