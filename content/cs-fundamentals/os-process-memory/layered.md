## Quick

[[process|Process]] là một chương trình đang chạy, có không gian [[virtual-memory|virtual memory]] riêng, bảng [[file-descriptor|file descriptor]] riêng và ít nhất một thread; các thread trong cùng process dùng chung bộ nhớ đó. Kernel chỉ cấp RAM thật khi page được chạm tới lần đầu, và dùng RAM còn trống làm [[page-cache|page cache]] cho file. **Bộ nhớ thật của process là [[rss|RSS]], không phải [[vsz|VSZ]]; `free` thấp chưa phải thiếu RAM vì page cache thu hồi được; khi không thu hồi được nữa thì [[oom-killer|OOM killer]] giết process bằng SIGKILL.**

## Interview

**Process và thread**: process là đơn vị cô lập: mỗi process có bảng page riêng nên không đọc được bộ nhớ của process khác. Thread là đơn vị được lập lịch: các thread chung heap, chung file descriptor, mỗi thread có stack riêng. Thread của Java (platform thread) là một thread của hệ điều hành, tỉ lệ 1:1.

**[[context-switch|Context switch]]**: kernel dừng thread này, lưu thanh ghi, chạy thread khác. Chi phí trực tiếp vài micro giây, chi phí gián tiếp lớn hơn vì cache CPU và [[tlb|TLB]] bị nguội. Vài nghìn thread tranh nhau ít core thì CPU mất phần đáng kể cho việc chuyển qua lại.

**Virtual memory**: process thấy một dải địa chỉ liên tục; kernel ánh xạ từng page (thường 4 KB trên x86) sang RAM khi process chạm vào lần đầu ([[page-fault|page fault]]). Vì vậy JVM với `-Xmx4g` có VSZ hàng GB ngay từ đầu nhưng RSS chỉ tăng dần.

**Page cache**: đọc ghi file đều đi qua page cache trong RAM. `free -h` hiện `free` nhỏ, `buff/cache` lớn là bình thường; cột cần nhìn là `available`.

**File descriptor**: file, socket, pipe đều là một số nguyên trong bảng của process. Giới hạn [[ulimit|`ulimit -n`]] chạm trần thì Java ném `IOException: Too many open files`, thường do quên đóng response hay stream.

**OOM killer**: RAM (hoặc memory limit của [[cgroup]]) hết và kernel không thu hồi được page cache nữa thì nó chọn process có điểm cao nhất (chủ yếu theo bộ nhớ đang chiếm) và giết bằng SIGKILL. Container báo [[oomkilled|OOMKilled]], exit code 137, JVM không kịp ghi log.

**Bẫy hay gặp**: thấy VSZ 12 GB tưởng leak; thấy `free` thấp đòi thêm RAM; đặt heap sát memory limit của container rồi bị OOMKilled; tăng `ulimit` để che chỗ rò socket thay vì alert khi số descriptor mở vượt 80% giới hạn.

## Deep

- **Process trong Linux**: kernel gọi cả process lẫn thread là task; thread chỉ là task dùng chung bảng page và bảng file descriptor. `fork` tạo process con dùng chung page theo [[copy-on-write|copy-on-write]] (Redis tạo snapshot bằng cách này, xem bài Redis bên trong), `exec` thay chương trình. Process con chết mà cha chưa đọc trạng thái thì thành zombie; trong container, PID 1 phải dọn zombie, nên script hay sinh process con nên chạy dưới `tini` hoặc `docker run --init`.
- **Đo context switch**: `vmstat 1` cột `cs` (cả máy), `pidstat -w -p <pid> 1` tách `cswch/s` (tự nhường vì chờ I/O, lock) và `nvcswch/s` (bị kernel giành CPU). `nvcswch/s` cao là thiếu CPU hoặc quá nhiều thread chạy được; kèm [[cpu-throttling|CPU throttling]] trong container thì latency đuôi tăng vọt. [[virtual-thread|Virtual thread]] chuyển giữa các tác vụ trong JVM, không cần kernel, nên rẻ hơn nhiều khi phần lớn thời gian là chờ I/O.
- **Load average** trên Linux đếm cả thread đang chạy, chờ CPU lẫn thread ở trạng thái `D` (chờ I/O không ngắt được). Load 40 trên máy 8 core chưa chắc là thiếu CPU: có thể là đĩa hay NFS treo. Xem `top` cột `%wa` và trạng thái thread.
- **VSZ và RSS của JVM**: JVM đặt trước (reserve) cả `-Xmx`, vùng compressed class space, code cache và stack của mọi thread, nên VSZ thường hàng GB tới hàng chục GB. RSS là page đã thật sự có trong RAM. `-XX:+AlwaysPreTouch` chạm mọi page của heap lúc khởi động: RSS lên đủ ngay, tránh page fault giữa giờ cao điểm, đổi lại khởi động chậm hơn. Xem nhanh bằng `ps -o pid,vsz,rss,cmd -p <pid>` hoặc `grep -E 'VmRSS|VmSize' /proc/<pid>/status`.
- **Minor và major page fault**: minor là page đã có trong RAM (page cache, page mới cấp) chỉ cần ánh xạ; major phải đọc từ đĩa, tốn từ hàng chục micro giây tới mili giây. Major fault tăng trong lúc app đang chạy là dấu hiệu RAM thiếu thật, page của chương trình bị đẩy ra rồi đọc lại. Đếm bằng `ps -o min_flt,maj_flt -p <pid>`.
- **Overcommit**: Linux mặc định (`vm.overcommit_memory=0`) cho cấp phát vượt RAM thật theo heuristic, vì phần lớn bộ nhớ xin về chưa chắc được dùng. Hệ quả: `malloc` hiếm khi trả lỗi; thiếu bộ nhớ lộ ra muộn, dưới dạng OOM killer, không phải lỗi cấp phát.
- **Page cache và ghi file**: `write` chỉ chép vào page cache rồi trả về; kernel ghi xuống đĩa sau (dirty page). Mất điện trước lúc đó là mất dữ liệu, nên database và Kafka gọi `fsync` khi cần bền. Kafka để phần lớn RAM cho page cache thay vì heap; PostgreSQL dựa cả vào `shared_buffers` lẫn page cache, MySQL với `O_DIRECT` bỏ qua nó (xem bài Storage engine: B+tree, LSM, WAL).
- **Page cache trong container**: cgroup tính cả page cache vào bộ nhớ của container. Kernel thu hồi cache trước khi giết ai, nên app đọc nhiều file vẫn chạy được sát limit. Nhưng kubelet tính "working set" = usage trừ `inactive_file`; cache đang hoạt động (`active_file`) bị coi là không thu hồi được, nên pod I/O nhiều có thể bị trục xuất (evict) dù không thiếu bộ nhớ thật. Theo dõi `container_memory_working_set_bytes`, không theo dõi `container_memory_usage_bytes`.
- **Đọc bộ nhớ trong container (cgroup v2)**: `/sys/fs/cgroup/memory.max` là limit, `memory.current` là mức đang dùng (gồm cả page cache), `memory.stat` tách `anon` và `file`, `memory.events` có bộ đếm `oom_kill`. Không phải cache nào cũng thu hồi được: file trên `tmpfs` (kể cả `emptyDir` với `medium: Memory`) và dirty page chưa ghi xuống đĩa vẫn chiếm chỗ, xem bài Bộ nhớ tăng dần & OOM.
- **mmap**: ánh xạ file thẳng vào virtual memory (`FileChannel.map`, `MappedByteBuffer`), đọc như đọc mảng, dữ liệu nằm ở page cache. Lucene và Elasticsearch dùng nhiều mmap nên đòi `vm.max_map_count` ít nhất 262144 (mặc định Linux 65530). Bộ nhớ mmap không nằm trong heap nhưng tính vào RSS.
- **File descriptor rò rỉ**: đếm bằng `ls /proc/<pid>/fd | wc -l` hoặc `lsof -p <pid>`; Micrometer có `process.files.open` và `process.files.max`, nên đặt alert ở khoảng 80%. Nhiều socket ở trạng thái `CLOSE_WAIT` (`ss -tanp state close-wait`) nghĩa là bên kia đã đóng mà app chưa `close()`, thường do không đóng body của HTTP response hay không dùng `try-with-resources`. Mỗi kết nối loopback trong cùng process tốn hai descriptor (client và phía accept).
- **`ulimit` và JVM**: mỗi process có giới hạn soft (đang áp dụng) và hard (trần soft được nâng tới). HotSpot trên Linux và macOS tự nâng soft lên bằng hard lúc khởi động (`-XX:+MaxFDLimit`, bật mặc định); đã kiểm trên macOS với JDK 27: soft 256, hard 400 thì JVM báo `getMaxFileDescriptorCount()` = 400, thêm `-XX:-MaxFDLimit` thì báo 256; trên Linux, `os_linux.cpp` của HotSpot làm cùng việc này. Vì vậy với Java, con số quyết định là hard limit. Đọc giới hạn thật của process đang chạy ở `/proc/<pid>/limits` (service systemd đặt bằng `LimitNOFILE`), đừng tin `ulimit -n` trong shell của mình.
- **Giới hạn số thread**: `unable to create native thread` đến từ `ulimit -u`, `pids.max` của cgroup, `kernel.threads-max`, hoặc hết virtual memory cho stack (mặc định `-Xss` 1 MB trên Linux x64, chỉ là phần đặt trước). Điều tra loại OOM này xem bài Bộ nhớ tăng dần & OOM.
- **OOM killer chọn ai**: mỗi process có `oom_score` (theo phần trăm bộ nhớ đang chiếm) cộng `oom_score_adj` (−1000 tới 1000). Kubernetes đặt `oom_score_adj` theo QoS: Guaranteed −997, BestEffort 1000, Burstable nằm giữa theo tỉ lệ request trên RAM của node. Khi container chạm memory limit của chính nó, kernel chỉ chọn trong cgroup đó. Dấu vết nằm ở `dmesg` hoặc `journalctl -k`: `Memory cgroup out of memory: Killed process 4321 (java) ... anon-rss:...`.
- **Swap**: đẩy page ít dùng ra đĩa để tránh OOM, đổi lại GC duyệt heap đụng page đã bị swap sẽ chậm cả giây. Server Java và Redis thường tắt swap hoặc đặt `vm.swappiness` thấp; kubelet mặc định không cho container dùng swap. Huge page và TLB xem bài CPU, bộ nhớ & các con số latency.
- **Tín hiệu và PID 1**: SIGTERM cho process cơ hội tắt êm (Spring Boot chạy graceful shutdown), SIGKILL (9) thì không. Kernel không áp hành vi mặc định của tín hiệu cho PID 1; JVM tự cài handler cho SIGTERM nên vẫn tắt đúng khi là PID 1, còn shell làm PID 1 thì không chuyển tiếp. Exit code 128 + số tín hiệu: 143 là SIGTERM, 137 là SIGKILL.
